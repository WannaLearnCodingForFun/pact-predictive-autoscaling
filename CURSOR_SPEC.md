# PACT — Implementation Spec

Predictive Autoscaling with Control-Theoretic enforcement, for Docker container pools.

This is the build spec for the system described in the paper
*"Deterministic Predictive Auto-Scaling of Docker Containers Using Temporal
Convolutional Resource Forecasting and Model Predictive Control."*

**How to use this file:** keep it open in Cursor as context. Work through the
phases in order. Do not ask the agent to build more than one phase at a time —
each phase has acceptance criteria, and a phase is not done until they pass.

---

## 0. Ground rules for the agent

- Python 3.11+. Type hints everywhere. `ruff` + `mypy` clean.
- **No fabricated numbers anywhere.** If a value is not measured or computed
  from data, it does not get written to a results file. No "example" metrics, no
  placeholder rows in CSVs, no hardcoded expected outputs in reports.
- Every module gets unit tests. Control logic gets tests with hand-computed
  expected values, not golden files generated by the code itself.
- Deterministic by construction: seed everything, and assert that two runs on
  identical input produce byte-identical scaling traces. This is a claim the
  paper makes — it must be enforced in a test, not assumed.
- Config via a single `configs/*.yaml`, loaded into frozen dataclasses. No magic
  numbers in function bodies.
- Structured logging (`structlog` or stdlib JSON). Every control tick logs:
  timestamp, observed metrics, forecast vector, computed demand, MPC solution,
  applied action, gate decisions, current margin.

## Phase 1 — Config, metrics, simulator

Build the parts that let you run experiments without Docker, so the control
logic can be developed and tested fast.

### 1.1 Config

`config.py` with frozen dataclasses mirroring the paper's symbols. Use the
paper's names so the code reads against the equations:

```python
@dataclass(frozen=True)
class TelemetryConfig:
    dt: float = 5.0                # Δt, control interval (s)
    alpha: float = 0.35            # α, EWMA smoothing
    window: int = 48               # L, input window length

@dataclass(frozen=True)
class ForecastConfig:
    horizon: int = 12              # H
    kernel_size: int = 3           # K
    depth: int = 4                 # D
    channels: int = 64             # C
    dropout: float = 0.10
    lr: float = 3e-3
    batch_size: int = 128
    kappa: float = 2.5             # κ, under-prediction penalty
    beta: float = 0.15             # β, horizon decay
    huber_delta: float = 1.0       # δ

@dataclass(frozen=True)
class CapacityConfig:
    u_target: float = 0.65         # u*
    r_target: float = 0.75         # r*
    mu: float = 40.0               # μ, per-replica service rate (req/s)
    slo_ms: float = 200.0          # ℓ_max
    ca2: float = 1.0               # c_a², arrival CV²
    cs2: float = 1.0               # c_s², service CV²

@dataclass(frozen=True)
class ControlConfig:
    q_up: float = 8.0              # q⁺ (under-provision penalty)
    q_down: float = 1.0            # q⁻
    r_act: float = 0.15            # r, actuation weight
    s_churn: float = 0.60          # s, churn weight
    n_min: int = 1
    n_max: int = 16
    delta_max: int = 4             # Δ_max
    deadband: int = 1              # θ
    cooldown_s: float = 60.0       # T_cool
    tau_c_s: float = 41.7          # τ_c, MEASURED cold start — do not guess

@dataclass(frozen=True)
class DriftConfig:
    eta: float = 0.2               # η, error smoothing
    kappa_gamma: float = 0.02      # κ_γ, margin gain
    gamma_min: float = 0.0
    gamma_max: float = 0.50
    xi: float = 1.0                # ξ, drift threshold
    drift_window: int = 60         # W
```

`tau_c_s` must be loaded from a file written by
`scripts/measure_cold_start.py`, not typed in. If that file is absent, the
loop refuses to start. This matters — the whole cold-start argument collapses if
τc is a guess.

### 1.2 Metrics

`eval/metrics.py` implements exactly the paper's Equations 29–33:

- `mae`, `rmse`, `mape`, `r2` — forecast accuracy
- `sla_violation_rate(p95_series, slo)` — Eq. 32, fraction of ticks over SLO
- `over_provision_ratio(n_series, n_required_series)` — Eq. 33, mean positive excess
- `scale_action_count(n_series)` — number of ticks where N changed
- `oscillation_count(n_series)` — sign reversals in ΔN within a rolling window
- `cost_per_1k_requests(n_series, dt, requests_served, unit_cost)`
- `decision_classification(n_applied, n_required)` — bucket each tick into
  {scale_up, hold, scale_down} for both series, return per-class precision /
  recall / F1 plus overall accuracy. **Recall on scale_up is the headline
  number** — a missed scale-up causes a violation; a missed scale-down costs money.

Every function pure, no I/O. Each gets a unit test with hand-computed values.

### 1.3 Analytical simulator

`sim/queue_model.py` — a pool of N servers, M/M/c-style, given an arrival rate
series. Exposes:

```python
class PoolSimulator:
    def step(self, arrival_rate: float, n_replicas: int) -> PoolState:
        """Returns utilisation, memory fraction, p95 latency, requests served."""
```

Critically, it must model **cold start**: a replica requested at tick `t`
becomes available at tick `t + ceil(τc/Δt)` and contributes nothing before then.
Without this the simulator makes predictive scaling look pointless.

Latency from the Kingman approximation (Eq. 18). Memory as a configurable
function of per-replica load plus a fixed baseline.

`sim/replay.py` drives the simulator from a trace at controllable time
compression.

**Acceptance criteria for Phase 1:**
- `pytest` green, `mypy` clean.
- A test drives the simulator with a step increase in arrival rate at a fixed
  replica count and asserts utilisation and latency rise as expected.
- A test asserts that a replica requested at tick t has no effect at tick
  t + τ/Δt − 1 and does have effect at t + τ/Δt.

## Phase 2 — Telemetry and features (Module 1)

### 2.1 Collector

`telemetry/collector.py`. Two backends behind one interface:

- `PrometheusCollector` — queries cAdvisor metrics via Prometheus HTTP API
- `SimCollector` — reads from `PoolSimulator`

Docker exposes **cumulative** counters. CPU is consumed nanoseconds; network and
block I/O are byte totals. Difference against the previous sample and divide by
Δt before the value means anything as a load signal. Get this wrong and
everything downstream is garbage.

Observation vector (Eq. 1): `[u, r, λ, ℓ_p95, N]`.

### 2.2 Features

`telemetry/features.py`:

- `EWMASmoother` — Eq. 2, one stored state per channel, recursive
- `MinMaxNormaliser` — Eq. 3, statistics fitted on the **training split only**
  and then frozen. Persist to disk with the model. `fit()` must raise if called
  after `freeze()`.
- `SlidingWindow` — Eq. 4, maintains the L×d tensor incrementally, O(1) per tick
- Derived channels:
  - `ρ(t) = λ(t) / max(N(t), 1)` — Eq. 5, per-replica arrival intensity.
    **This channel is why the predictor forecasts exogenous demand instead of
    its own past scaling actions.** It is not optional.
  - time-of-day as `sin(2πt/86400)`, `cos(2πt/86400)`

**Acceptance criteria:**
- Test that the normaliser refuses to refit after freezing.
- Test that incremental windowing produces the same tensor as naive recomputation.
- Test that cumulative-to-rate conversion is correct across a counter reset
  (container restart → counter goes to zero; must not produce a negative rate).

## Phase 3 — Forecaster (Module 2)

### 3.1 Model

`forecast/tcn.py`, PyTorch:

- Dilated **causal** convolutions, dilation `d_l = 2^(l-1)`. Causality enforced
  by left-padding then trimming the right. Write a test that shifts one future
  input sample and asserts the output at earlier timesteps is unchanged — a
  non-causal kernel leaks the future and produces a model that cannot be deployed.
- Gated activation (Eq. 7): `tanh(W_f * h) ⊙ σ(W_g * h)`
- Residual blocks (Eq. 8) with 1×1 conv on the skip path
- Assert at construction that receptive field `R = 1 + 2(K-1)(2^D - 1) ≥ L` (Eq. 9)
- Linear head emitting all H steps in one pass (Eq. 10), output shape `(H, 2)`
  for CPU and memory. **Not autoregressive** — single forward pass per tick.

### 3.2 Loss

`forecast/losses.py` — Eq. 11–13:

```
L = (1/H) Σ_h w_h · c(e_h) · Huber_δ(e_h)
c(e) = κ if e < 0 else 1        # under-prediction costs more
w_h = softmax(-β(h-1))          # near-term steps weighted higher
```

Test that with κ > 1 the loss for a given negative error strictly exceeds the
loss for the same-magnitude positive error.

### 3.3 Training

`forecast/train.py`:

- **Chronological splits, 70/15/15. Never shuffle before splitting.** Shuffling a
  time series leaks the future into training and inflates reported accuracy
  enough to invalidate the result. Add an assertion that
  `max(train_timestamps) < min(val_timestamps) < min(test_timestamps)`.
- Early stopping on validation loss, restore best weights
- Log per-epoch train and validation loss to `results/training.csv`
  (columns: `epoch,train_loss,val_loss`) — this is Fig. 10
- Export to ONNX, verify ONNX output matches PyTorch within 1e-5
- Report parameter count and measured single-tick CPU inference latency

### 3.4 Inference

`forecast/infer.py` — ONNXRuntime, CPU provider, single-threaded. Must complete
well inside Δt; assert and log if a tick exceeds budget.

**Acceptance criteria:**
- Causality test passes.
- Asymmetry test passes.
- Chronological split assertion present and tested.
- Horizon-error curve written to `results/horizon_error.csv`
  (`horizon,mae,rmse`) — this is Fig. 3, and error should *increase* with h. If
  it doesn't, something is wrong.

## Phase 4 — Capacity mapping (Module 3)

`capacity/mapper.py`, implementing Algorithm 1 lines 7–16 exactly:

```python
def map_to_demand(forecast, n_current, gamma, cfg) -> list[int]:
    # per horizon step h:
    #   λ̂      = û(t+h) · N(t) · μ                     Eq. 14
    #   n_cpu   = ceil((1 + γ) · λ̂ / (μ · u*))          Eq. 15, 16
    #   n_mem   = ceil(r̂(t+h) · N(t) / r*)
    #   n       = max(n_cpu, n_mem)                      Eq. 17
    #   while latency_est(n, λ̂) > slo and n < n_max:     Eq. 18
    #       n += 1
    #   yield clip(n, n_min, n_max)
```

Pure function, no state. The while loop terminates because n strictly increases
and is bounded by `n_max` — put that in a test.

Also implement the horizon check (Eq. 19) as a validator run at startup:

```python
assert H * dt >= tau_c + dt_ctrl, (
    f"Horizon {H*dt}s does not cover cold start {tau_c}s — "
    "forecast is not actionable"
)
```

This assertion is the formal version of the paper's central argument. It should
be impossible to run a misconfigured system.

**Acceptance criteria:**
- Test: zero forecast → `n_min`.
- Test: forecast above what `n_max` can serve → returns `n_max`, does not hang.
- Test: raising γ never decreases demand (monotonicity).
- Test: the horizon assertion fires for H too small.

## Phase 5 — MPC controller (Module 4)

This is the core contribution. Build it carefully.

### 5.1 Optimisation

`control/mpc.py`, implementing Eq. 20–24:

- Plant model: `N(t+1) = N(t) + u(t − τ)`, `τ = ceil(τc/Δt)` — Eq. 20.
  The dead-time term is what makes the controller act early.
- Cost (Eq. 21): tracking + actuation + churn
- Asymmetric tracking weight (Eq. 22): `q⁺` when under the demand, `q⁻` when over
- Constraints (Eq. 23): pool bounds, rate limit, integrality
- Solve by relaxing integrality → QP → round first element → repair feasibility.
  Use `scipy.optimize` or `cvxpy` with OSQP. Log solve time; it must be well
  under a millisecond.
- Apply only `u*[1]` (Eq. 24), re-solve next tick.

The asymmetric weight makes the cost piecewise-quadratic and not a single QP.
Two acceptable approaches — pick one and document it:
(a) iterate: solve with a guessed active sign pattern, update signs, re-solve,
    2–3 iterations converges in practice;
(b) since `Δ_max` and H are small, enumerate candidate first actions in
    `[-Δ_max, +Δ_max]`, evaluate the exact piecewise cost for each with the rest
    of the horizon solved greedily, take the argmin. Exact, trivially correct,
    and fast enough at these sizes. **Prefer (b) for the first version** — it is
    easier to test and you can swap in (a) later if profiling demands it.

### 5.2 Gates

`control/gates.py` — Eq. 25 plus projections. **Order matters and must be
enforced in this sequence:**

1. round the relaxed solution
2. clip to `±Δ_max`
3. clip so `N + u ∈ [n_min, n_max]`
4. deadband: if `|u| < θ` → 0
5. cooldown: block scale-down within `T_cool` of a scale-up

Feasibility (1–3) before gating (4–5), so the guard rails cannot be defeated by
an unusual forecast. Test each step independently and test the composition.

### 5.3 Reactive safety ceiling

`control/safety.py` — **this is not in the current paper draft and you should
add it.**

The design as written has no fallback: if the forecast misses an unprecedented
burst, nothing catches it. Add an override that bypasses the MPC and the gates
entirely:

```python
if observed_utilisation > u_emergency:   # e.g. 0.92
    return immediate_scale_up(...)       # ignores deadband and cooldown
```

Cite reference [20] (AgileSphere, predictive-reactive) in the paper when you
write this up. It closes the most obvious line of attack on the design, and it
makes the system honest: a purely predictive autoscaler that has never seen a
pattern before will fail, and pretending otherwise is indefensible.

Log every override. Override frequency is itself a result worth reporting.

**Acceptance criteria:**
- Test: constant demand equal to current N → `u = 0` (no churn at equilibrium).
- Test: step increase in demand → controller acts `τ` ticks **before** the
  demand arrives, not at arrival. This is the single most important test in the
  project — it is the paper's whole claim.
- Test: alternating demand within the deadband → zero actions.
- Test: raising `s_churn` monotonically decreases the action count on a fixed
  noisy demand trace.
- Test: `q⁺ ≫ q⁻` produces higher replica counts than `q⁺ = q⁻` on the same trace.
- Test: safety ceiling fires regardless of cooldown state.
- Determinism test: same input trace twice → identical action sequence.

## Phase 6 — Drift monitor (Module 5)

`drift/monitor.py` — Eq. 26–28:

- Tracking error `e(t) = N_required_observed(t) − N_predicted(t | t−τ)`.
  Needs a ring buffer of past predictions so the comparison is against the
  prediction that referred to *this* instant. Off-by-τ here silently breaks
  everything.
- Smoothed error `ē(t) = η e(t) + (1−η) ē(t−1)`
- Clipped integral margin update: `γ ← clip(γ + κ_γ ē, γ_min, γ_max)`
- Drift trigger: `|ē| > ξ` for W consecutive ticks → schedule incremental refit
  in a separate process; swap weights atomically so the control loop never blocks

**Acceptance criteria:**
- Test: sustained under-prediction drives γ up and it saturates at `gamma_max`.
- Test: sustained over-prediction drives γ down to `gamma_min`.
- Test: a single large error spike does not move γ more than `κ_γ · spike`.
- Test: the prediction ring buffer aligns correctly — feed known predictions and
  known outcomes and assert the computed error.

## Phase 7 — Actuation and the loop

`actuation/docker_backend.py`:

- `docker compose up -d --scale <service>=<n>` via subprocess, or the Docker SDK
- Reconciliation: poll observed running/healthy count until it matches desired
  or a timeout expires. Idempotent — calling with the current count is a no-op.
- Never block the control loop on reconciliation; run it async and report state.

`loop.py` wires M1 → M2 → M3 → M4 → M5 on a fixed Δt tick with drift
compensation (use `time.monotonic()` and absolute deadlines, not `sleep(dt)`,
or the loop drifts). Log every field listed in section 0.

**Acceptance criteria:**
- Loop runs 200 ticks against `SimCollector` + `dry_run` backend with no
  exceptions and stable tick timing.
- Loop runs against the real testbed and successfully scales a service up and down.

## Phase 8 — Baselines

All baselines must receive **identical telemetry, the same Δt, the same
actuation path, and the same `n_min`/`n_max`/`Δ_max`**. The only thing that
varies is the decision mechanism. An under-tuned baseline produces an
"improvement" that is an artefact of the protocol, and a competent reviewer will
ask how each baseline was tuned.

- `baselines/reactive.py` — the Kubernetes HPA control law:
  `desired = ceil(N · u_observed / u_target)`, with HPA's tolerance band and
  stabilisation window. Reference [4] characterises this law precisely; follow it.
- `baselines/arima_ctl.py` — `statsmodels` ARIMA, order selected on the
  validation split, feeding the same Module 3 mapping with a fixed margin
- `baselines/lstm_ctl.py` — LSTM matched to the TCN on parameter count, trained
  with plain (symmetric) Huber, same mapping
- `baselines/static.py` — fixed N sized to the trace peak

Also needed for Table 5: Bi-LSTM, GRU and a small Transformer, as
**forecasters only** (same Module 3 + Module 4 downstream), so that table
isolates forecaster choice.

Each baseline gets a tuning script that searches its parameters on validation
with the **same budget** as the proposed method, and writes the chosen
configuration to `results/baseline_tuning.json`.

### 9.1 Datasets

`scripts/download_traces.py`:

- **D1** — 1998 FIFA World Cup HTTP trace. Parse to request counts per 5 s

- **D2** — Bitbrains GWA-T-12 `fastStorage`. 5-minute samples; resample to 5 s

### 9.4 Ablations

`eval/ablation.py` — six configs in `configs/ablations/`, each disabling exactly
one component:

| Config | Change |
|---|---|
| `no_asym_loss.yaml` | `kappa: 1.0` |
| `no_mpc.yaml` | apply `Ñ(t+1)` directly, skip Module 4 |
| `no_churn.yaml` | `s_churn: 0.0` |
| `no_coldstart.yaml` | `tau_c_s: 0.0` |
| `no_adaptive_margin.yaml` | freeze γ, disable Module 5 |
| `no_rho_channel.yaml` | drop the per-replica intensity feature |

Expected directions — if a result contradicts these, investigate before
reporting, because it usually means a bug:
- `no_asym_loss`: MAE **improves**, SLA violations **worsen**. This is the
  cleanest demonstration in the whole paper that lower forecast error is not
  the objective.
- `no_mpc` and `no_churn`: forecast metrics unchanged, action count rises sharply.
- `no_coldstart`: violations rise at burst onset, steady state unaffected.
- `no_rho_channel`: MAE worsens.

### 9.5 Hyperparameter search

`eval/hpsearch.py`:

- Architectural and optimisation parameters (L, K, D, C, dropout, lr, batch):
  random search over a bounded grid, **validation split only**
- Control parameters (q⁺/q⁻, r, s, θ, T_cool): one-dimensional sweeps, reported
  as curves — their effect on the violation/cost trade-off is near-monotone and
  a curve is more informative than a selected point
- **H is not searched.** It is fixed by Eq. 19. Treating it as free would permit
  horizons too short to be actionable.
- Touch the test split exactly once, after the configuration is frozen. Enforce
  this in code: a `SplitGuard` that raises if test data is accessed more than
  once per process.

## Phase 10 — Testbed

`testbed/docker-compose.yml`:

- `service` — the workload. A stateless HTTP app with a **configurable
  per-request CPU cost** and a per-container concurrency cap.
- `nginx` — least-connections upstream, so a newly registered replica starts
  absorbing traffic immediately instead of waiting for round-robin
- `cadvisor`, `prometheus`
- `pact` — the controller as a sidecar with a fractional CPU reservation, so its
  own consumption is counted against the same budget as the workload

`scripts/measure_cold_start.py` — times from issuing the scale command to the
first successful request served by the new replica. Run with warm and cold image
cache, 20 repetitions each, write mean and standard deviation to
`results/cold_start.json`. The loop reads τc from this file.

### The single-host caveat, and what to do about it

On one host, adding replicas only adds capacity if the bottleneck is
**per-container**, not host-wide. If your workload is host-CPU-bound, replicas
just partition the same cores and the entire experiment measures nothing.

So: make the workload single-threaded per container with a concurrency cap, so
throughput genuinely scales with replica count up to core count. Set `n_max`
below the physical core count and record both in Table 2.

Then add `testbed/swarm/` — the same stack on a 2–3 node Docker Swarm. Even one
run there materially strengthens the paper and pre-empts the obvious question
about whether single-host replication means anything.

## Priority order if time runs short

If you can only finish part of this, finish it in this order. Phases 1–5 plus
one baseline gives you a defensible paper with real numbers.

1. **Phases 1, 2, 3, 4, 5** — core pipeline, simulator-only
2. **Phase 8, reactive baseline only** — you need one comparison to say anything
3. **Phase 9.3** — export, so figures and tables come from data
4. **Phase 9.4 ablations** — cheap once the pipeline runs, and the highest-value
   result in the paper
5. **Phase 6** — drift monitor
6. **Phase 10** — real Docker testbed
7. Remaining baselines, hyperparameter search, Swarm

Simulator-only results are publishable if you say plainly that they are
simulator-only. Fabricated testbed results are not publishable at all.
